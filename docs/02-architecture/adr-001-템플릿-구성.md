# ADR-001: phaser-starter 템플릿 구성

## 상태

승인됨 (2026-09-12)

## 배경

MergeDrop(첫 Phaser 웹 게임)을 만들면서 빌드 설정, 린트, 테스트, GitHub Pages 배포 워크플로를
한 번 구축했다. 두 번째 게임을 시작할 때 이걸 전부 다시 만들어야 한다는 것이 문제였다.

전역 하네스(`~/.claude`)는 CLAUDE.md·권한·hook·스킬·커맨드를 어느 프로젝트에서든 자동으로
제공하지만, **프로젝트 안의 파일은 만들어주지 않는다.** `vite.config.ts`, `tsconfig.json`,
`eslint.config.js`, `.github/workflows/deploy.yml`은 매번 다시 써야 했다.

## 결정

**GitHub 템플릿 저장소**로 만든다. `new-project` 스킬을 확장하는 대신 이 방식을 택했다.

```bash
gh repo create MyGame --template y3games/phaser-starter --public --clone
```

담는 것:

- MergeDrop에서 검증된 빌드·린트·테스트·CI 설정 그대로
- 씬 3분할, 순수 규칙 레이어, `ScoreService` 추상화의 **작동하는 최소 예시**
- 실플레이로 얻은 함정들을 `CLAUDE.md`의 Gotchas에 정리

`base` 경로는 하드코딩하지 않고 `GITHUB_REPOSITORY` 환경변수에서 저장소 이름을 읽어 도출한다.

## 이유

**스킬 확장이 아니라 템플릿인 이유**: 스킬은 "이렇게 만들어라"는 지시문이라 매번 파일을 다시
생성해야 하고, 그 과정에서 미묘하게 달라진다. 템플릿은 **이미 검증된 파일 그 자체**를 복제하므로
"MergeDrop에서는 되는데 여기서는 안 되는" 종류의 차이가 생기지 않는다.

**빈 껍데기가 아니라 돌아가는 데모를 넣은 이유**: 설정만 있는 템플릿은 처음 실행했을 때 아무것도
안 뜨므로, 문제가 생겨도 그게 템플릿 탓인지 내 코드 탓인지 알 수 없다. 데모가 돌아가면 파이프라인이
정상이라는 것을 확인한 상태에서 시작할 수 있다.

**`base`를 환경변수에서 도출하는 이유**: MergeDrop은 `base: '/MergeDrop/'`로 하드코딩했다.
템플릿에서 이걸 그대로 두면 새 프로젝트에서 반드시 고쳐야 하고, 잊으면 배포본의 모든 에셋이
404가 난다. 증상이 "빈 화면"뿐이라 원인 찾기도 어렵다. 자동 도출은 이 실수 자체를 없앤다.

**Phaser 3.90 고정**: `npm install phaser`는 4.x를 설치한다. 4는 렌더러가 새로 쓰인 메이저
개편이라 API가 다르고 자료가 거의 없다. 템플릿에서 버전을 고정해 매번 판단하지 않게 한다.

## 영향

- **템플릿과 실제 프로젝트가 갈라진다.** MergeDrop에서 새로 배운 것이 자동으로 템플릿에 반영되지
  않는다. 의미 있는 개선은 수동으로 옮겨야 한다.
- **MergeDrop은 여전히 `base`를 하드코딩하고 있다.** 이미 배포되어 동작하므로 급하지 않지만,
  두 프로젝트의 방식이 다르다는 점은 알고 있어야 한다.
- `vite.config.ts`가 `process.env`를 읽으므로 `@types/node`가 devDependency로 들어간다.
  `tsconfig.json`의 `types`에 `"node"`가 추가되어 있어, 게임 코드에서도 Node 전역이 타입상
  보인다. 실제로 쓰면 브라우저에서 깨지므로 쓰지 말 것.
